# Benchmark 2026-10-25 (phase 3)

First T3 run with commerce scenarios (doc 10 §5.3, §6.4): shop archive, simple and variable product pages, cart add and cart view, on dataset M. It is the indicative FlexaCommerce versus WooCommerce comparison that the phase 3 exit asks for (doc 07). Raw data: [`2026-10-25/M-php8.2-1vu/`](2026-10-25/M-php8.2-1vu/); the `*.jsonl` logs are gzipped, so run `gunzip -r` on a copy before `summarize.php`.

**Status of the numbers.** Per-request counters (queries, peak memory, rows read, CPU time, worker RSS, HTML bytes) are deterministic and are the result of this run. Latency is **indicative only**. Eleven of the thirteen rows fail the doc 10 validity rule (spread of the run p95s ≤ 10 %), with spreads of 10.3 to 71.4 %; only `home/wc` and `shop/wc` pass. The cause is the machine, not the method: see the run order note below.

**Run order note.** In run 3 the fxc block ran last, and every fxc scenario has its slowest p95 there (cart-add 25 ms against 15 and 15). CPU time per request rose by a similar ratio in that block (cart-add 10.7 ms against 6.8), while queries and rows read did not change. So the drift comes from the host slowing down late in the run (load, thermal), and the fxc spreads say more about the laptop than about FlexaCommerce.

## Reading the counters

- **Home.** fxc against core: +0 queries, +0 rows read, +62 KB peak memory. P1 still holds with the phase 3 code loaded (T1 budget 256 KB).
- **Shop rows read.** About 10,000 of the 10,706 rows per fxc request come from the WordPress core archive query (`SQL_CALC_FOUND_ROWS` over the product type), measured as a delta of the global `Innodb_rows_read`. The plugin's own share is small; reducing the core count (no found-rows, a cached total) is a phase 5 catalog task, not a phase 3 regression.
- **Shop parity.** The two shop pages are not equal work. The fxc archive uses the theme's archive template, which shows 10 products per page (`posts_per_page`); the WooCommerce shop shows 16. WooCommerce also puts 21 script tags and 11 linked stylesheets on the page, against 7 script tags and no linked stylesheet for fxc. Per product shown, WooCommerce spends about 8.4 ms (134 ms / 16) and fxc about 3.8 ms (38 ms / 10), still indicative. The per-page setting is a phase 5 item.
- **Product pages.** WooCommerce reads 2,944 rows (simple) and 4,578 (variable) per request against 175 and 238 for fxc. The WooCommerce page also does more: it renders related products, which fxc does not have yet, so part of the gap is a feature difference. This run does not break the rows down by query.
- **Cart.** fxc cart-add runs 16 queries and cart-view 14, against WooCommerce's 69 and 74. Both fxc requests stay under 5.1 MB peak memory. These match the T1 counts for P4q (4 plugin queries) and P5q (6 plugin queries); the rest is WordPress boot and the REST server.
- **Worker RSS.** An fxc worker settles at about 47 MB, a WooCommerce worker at about 82 MB, on every scenario.

## What this run does not support

- Any latency figure as a result, including the fxc against WooCommerce ratios. They point the same way on every scenario, and by a wide margin, but the doc 10 rule needs a quiet reference machine (Q18) and spreads ≤ 10 %.
- 10 or 25 VUs, a second PHP version, or the tuned WooCommerce configuration (doc 10 §6.3).
- Checkout, orders and account pages, which come in phase 4.

./bench.sh run home shop simple variable cart-add cart-view
