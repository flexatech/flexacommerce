# Benchmark 2026-10-25 (phase 4)

T3 run for the phase 4 exit (doc 07): checkout at 1, 10 and 25 virtual users (P6), and the catalog pages at 1 and 25 virtual users for the concurrency targets C1 and C2 (doc 10 §4.2), on dataset M. Raw data: [`2026-10-25-phase4/`](2026-10-25-phase4/), one folder per batch (`p6-1vu`, `p6-10vu`, `p6-25vu`, `c1-1vu`, `c1-25vu`). The `*.jsonl` logs are gzipped, so run `gunzip -r` on a copy before `summarize.php`.

**Status of the numbers.** Per-request counters (queries, peak memory, CPU time, rows read, worker RSS) are deterministic and are the result of this run. Latency and req/s are **indicative only**: one row of 26 (`checkout/wc` at 10 VU) passes the doc 10 validity rule (spread of the run p95s ≤ 10 %). The machine is still the developer laptop, and at 25 VU it is short of CPU (below). Every run had 0 % errors, every checkout run placed 500 orders, and no run had a stock error.

## Checkout scenario

Each iteration is a new guest buying five simple products (stock 1,000,000 each, set by `prep-checkout.php`) with cash on delivery and one US flat rate:

| Step | fxc | wc | Counted |
|---|---|---|---|
| Nonce | `GET …/flexacommerce/v1/store/cart` | `GET …/wc/store/v1/cart` | no |
| Add 5 lines | 5 × `POST …/store/cart/items` | 5 × `POST …/cart/add-item` | no |
| Checkout form | `GET …/store/checkout` (the checkout token) | none | no |
| Place order | `POST …/store/checkout`, 201 | `POST …/wc/store/v1/checkout`, 200 | yes |

Latency, queries, peak memory and CPU time describe the order request alone. Rows read per request and req/s cover the whole flow: the MySQL counters include the prep requests, and req/s is the rate of whole checkouts.

Parity choices:

- **Emails.** Both stores defer the order emails. WooCommerce hands them to Action Scheduler (`woocommerce_defer_transactional_emails`). FlexaCommerce renders them during the request and queues the result in a transient for a cron event (its `defer_emails` setting), so the template work stays in the measured request and only the send moves out. The mail server is out of the numbers for both (`pre_wp_mail`).
- **Rate limit.** Every k6 request comes from one IP, and FlexaCommerce allows 30 checkouts per IP per 10 minutes (doc 06 §2.9). WooCommerce's Store API rate limiting is off by default, so the bench mu-plugin turns the FlexaCommerce per-IP limit off (`flexacommerce.rate_limit.checkout_ip`). The per-session limit stays on; each iteration is a new session. A first attempt with the limit on answered 429 to every measured request after the warm-up and was discarded.

## Reading the counters

- **Checkout queries.** The fxc order request runs 65 queries for five lines, WooCommerce 913. The fxc count includes WordPress boot and the REST server; the plugin's own share is gated in T1 as P6q (budget 60, measured 54 fixed plus one per line).
- **Checkout memory.** The fxc peak is 5.3 to 6.5 MB against 12.2 MB for WooCommerce. The fxc peak is about 1 MB higher in the 1 VU batch (4 workers) than in the other two; this run does not show why.
- **Rows read.** About 1,440 rows per fxc checkout and 9,700 to 10,100 per WooCommerce checkout, both for the whole flow. Run 3 of the 25 VU fxc block reports 140,274 rows per checkout. Its queries, memory and CPU match runs 1 and 2, and the counter is a global `Innodb_rows_read` delta, so something outside the request (a MySQL background task, most likely) read rows during that block. The median (1,438) is not affected.
- **Worker RSS.** An fxc worker stays at about 46 to 48 MB on every scenario and load, a WooCommerce worker at 77 to 85 MB.

| Target | Value | This run | Status |
|---|---|---|---|

| P6 checkout p95 ≤ 500 ms at 10 VU | fxc 161 ms | indicative, spread 26.7 % | not gated |
| P6 at 25 VU, report only | fxc 322 ms | indicative | reported |
| P6 no oversell | 0 stock errors in 18 runs | deterministic | pass |
| C1 p95 at 25 VU ≤ 2 × p95 at 1 VU, workers ≥ VUs | fxc 3.9 to 6.5 ×, core 8.2 × | indicative | not met on this machine |
| C2 req/s where p95 first exceeds its budget, and worker RSS | checkout: fxc not reached at 25 VU (28.0 checkouts/s, p95 322 ms); wc between 1 VU (2.6/s, 249 ms) and 10 VU (8.9/s, 1,129 ms). RSS in the tables above | req/s indicative, RSS deterministic | reported |

**C1 on the laptop.** The ratio is above 2 for every store and scenario, and the largest one belongs to core with no plugin at all (8.2 ×). With 25 workers busy on 8 CPUs, requests queue for CPU: CPU time per request rises from about 32 ms to 49 ms on fxc home while queries and rows stay the same. So this machine cannot show whether FlexaCommerce meets C1. It needs the reference machine (Q18), with at least as many cores as the target allows, and C1 stays open until then. On the one page both have, fxc home (6.3 ×) rises less than core home (8.2 ×), so the plugin does not add to the slowdown that the machine causes.

The query and memory budgets (P6q, P6m and the earlier ones) are gated in the T1 harness (`tests/Integration/Performance/`), not here. The run above agrees with them.

## What this run does not support

- Any latency or req/s figure as a result, including the fxc against WooCommerce ratios. The single valid row (`checkout/wc` at 10 VU) has no valid fxc row to compare with.
- C1 as passed or failed for FlexaCommerce (see above).
- A second PHP version, the tuned WooCommerce configuration (doc 10 §6.3), or a payment gateway other than cash on delivery.
- The cost of sending the deferred emails; that work happens in a later cron request in both stores and is not measured.

## Reproduce

```sh
cd tools/bench
./bench.sh up
./bench.sh setup M
./bench.sh prep-checkout

batch() { # workers vus scenarios...
  local w=$1 v=$2; shift 2
  FPM_WORKERS=$w docker compose -f docker/compose.yml up -d --force-recreate php nginx
  docker compose -f docker/compose.yml exec -T php chmod 777 /var/log/bench
  FPM_WORKERS=$w VUS=$v ./bench.sh run "$@"
}
batch 4 1 checkout
batch 10 10 checkout
batch 25 1 home shop simple variable
batch 25 25 home shop simple variable
batch 25 25 checkout
```

The worker count only changes when the PHP container is recreated, which is why each batch recreates it.
