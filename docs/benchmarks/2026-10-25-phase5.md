# Benchmark 2026-10-25 (phase 5)

T3 run for the phase 5 exit (doc 07): the doc 10 §6.4 scenario set on dataset M, FlexaCommerce against WooCommerce in its default and its tuned configuration (§6.3), at 1 and 10 virtual users. The run found a slow visibility filter on the FlexaCommerce listing pages; it was fixed and the listing pages and the journey were measured again. Raw data: [`2026-10-25-phase5/`](2026-10-25-phase5/), one folder per batch (`t3-1vu`, `t3-10vu` before the fix, `fix-1vu`, `fix-10vu` after it), plus `wc-tuned.json`. The `*.jsonl` logs are gzipped, so run `gunzip -r` on a copy before `summarize.php`.

**Status of the numbers.** Per-request counters (queries, peak memory, CPU time, rows read, worker RSS, HTML bytes) are deterministic and are the result of this run. Latency and req/s are **indicative only**: 3 of 76 rows in the first run pass the doc 10 validity rule (spread of the run p95s ≤ 10 %), and no row of the two reruns does. The machine is still the developer laptop (Q18). Every run had 0 % errors, every checkout run placed 500 orders, every journey run completed 100 visits, and no run had a stock error.

## The visibility filter (found and fixed in this run)

The fxc listing pages read about 150,700 rows per request, against 11,900 to 14,400 for WooCommerce, and were slower than WooCommerce at 1 and 10 VU while running a fifth of its queries. The cause was the catalog visibility filter (doc 03: `_fxc_visibility`, products hidden from the catalog or from search). `ShopQuery` added it as a `meta_query` (`NOT EXISTS` or `NOT IN`), which WP_Query turns into two `LEFT JOIN`s on `wp_postmeta` and a `GROUP BY wp_posts.ID`. MySQL then built a temporary table over all 10,000 published products and sorted it before taking the 12 it shows. Dataset M has no hidden product, so the whole cost bought nothing.

The filter is now a correlated `AND NOT EXISTS (SELECT 1 FROM wp_postmeta … meta_key = '_fxc_visibility' AND meta_value IN (…))` added through `posts_where` for queries that carry the `fxc_visibility` query var (`ShopQuery::hide_in()`, used by the shop loop, the Query Loop variation and related products). The filter callback is added on the first query that needs it, so pages without a product list keep their callback count (P1). The query has no join and no `GROUP BY` (`ShopQueryTest::test_visibility_adds_no_join`). EXPLAIN shows a backward scan of the `type_status_date` index that stops at the page size, and an antijoin on a materialized subquery of the `_fxc_visibility` rows (estimate 17,780 rows). Query counts did not change.

## Reading the counters

- **Queries.** FlexaCommerce runs 23 to 32 queries on catalog pages against 104 to 123 for WooCommerce, 14 to 24 on the cart against 67 to 127, and 65 on the order request against 913 (wct 830). A journey visit costs 243 queries against 1,444 (wct 1,360). On the blog post and the blog home, fxc runs the same queries and reads the same rows as core.
- **Product pages.** The fxc simple and variable pages grew from 21 and 22 queries in phase 4 to 29 and 32: the phase 5 blocks (gallery, breadcrumbs, related products) add them. They read more rows than WooCommerce (4,700 to 4,800 against 2,950 to 4,600); this run does not show which query.
- **Memory.** fxc peaks at 5.2 to 7.3 MB per request, WooCommerce at 11.0 to 13.9 MB. An fxc worker stays at 46 to 50 MB RSS, a WooCommerce worker at 77 to 88 MB.
- **CPU.** PHP CPU time per request is 0.35 to 0.5 of WooCommerce's on every catalog and cart page and 0.2 on the order request.
- **HTML.** The fxc commerce pages are 0.4 to 0.65 of the WooCommerce page size (65 KB against 132 KB on the simple product), with 2 script tags and 1 stylesheet against 10 to 20 and 8 to 15. On the blog home the sizes are close; WooCommerce adds 4 KB, 6 to 8 script tags and 5 stylesheets.
- **Tuned against default.** The tuned WooCommerce saves 2 queries on every page, 83 on the order request and about a third of the rows read by a checkout (6,388 against 9,737). Its latency does not differ from the default in a way this run can show.

## What this run does not support

## Reproduce

```sh
cd tools/bench
./bench.sh up
./bench.sh setup M
./bench.sh prep-checkout

batch() { # workers vus scenarios...
  local w=$1 v=$2; shift 2
  FPM_WORKERS=$w docker compose -f docker/compose.yml up -d php
  FPM_WORKERS=$w VUS=$v RUNS=3 N=500 WARMUP=50 JOURNEY_N=100 JOURNEY_WARMUP=10 ./bench.sh run "$@"
}
all="blog-post home collection shop shop-20 simple variable cart-add cart-view cart-page checkout journey"
batch 4 1 $all
batch 10 10 $all
# after the visibility fix
STORES="fxc wc" batch 4 1 collection shop shop-20 journey
STORES="fxc wc" batch 10 10 collection shop shop-20 journey
```

The worker count only changes when the PHP container is recreated, which is why each batch recreates it.
